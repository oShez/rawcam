# How MCRAW Records Compressed RAW Video on a Phone

*And what RawCam should take from it. Research date: 2026-09-13.*

## 0. The short answer

MotionCam Pro keeps up with RAW video on a phone through three decisions, none of them clever on its own:

1. **A codec that is cheap per pixel.** Every 64 same-colour samples get one reference value and one bit width, and the leftovers are packed at that fixed width. There is no prediction and no entropy coder. Encoding and decoding are branch-free SIMD loops.
2. **A large RAM buffer between the camera and everything else.** Each frame is copied out of Android's `ImageReader` into a pre-allocated pool the moment it arrives, so the camera never waits on compression or storage. The pool is sized in megabytes (512 MB to 4 GB in the 2022 app's settings), not in frames.
3. **Parallel writes.** Each output file gets its own I/O thread, and the user can add a second storage location so two files are written at once.

The premise needs one correction before anything else. **MotionCam does drop frames.** When the pool is empty, the copy thread discards the incoming frame. Users report that 4K60 on a Pixel 7 Pro's internal storage lasts 30 to 60 seconds before the buffer fills. What MotionCam achieves is absorbing stalls long enough, with a codec cheap enough, that ordinary takes finish before the buffer runs out.

## 1. What can be known, and how

Three kinds of source exist, and they are not equally reliable.

**The decoder is open and current.** MotionCam publishes `mirsadm/motioncam-decoder` under Apache-2.0. It reads today's files and names two compression types: `MOTIONCAM_COMPRESSION_TYPE = 7` (current) and `MOTIONCAM_COMPRESSION_TYPE_LEGACY = 6`. A decoder fixes the bitstream exactly, so the file format is known with certainty.

**The encoder has never been open.** The original MotionCam app was GPLv3 until 2022, and a copy of its last revision survives at `TadiT7/motioncam`. Even there, the encoder is a header (`RawEncoder.h`, declaring `encode`, `encodeAndBin` and `decode`) plus a precompiled static library, `libs/libmotioncam-encoder.a`. Nobody outside MotionCam has seen the compressor's source. Anything this article says about *how* the encoder makes its choices is inferred from what the decoder requires, and is marked as inference.

**The pipeline is known from 2022, and partly confirmed since.** The archived app contains the full capture pipeline in source: frame intake, the buffer pool, compression threads, file writers and settings. Current MotionCam Pro is closed. Two things support treating the 2022 pipeline as still representative: users in an XDA thread started in January 2023 describe the same "memory buffer" and "split data" behaviour, and the archive's codec turns out to be exactly what today's decoder calls legacy (section 4), so the lineage is continuous.

Two independent readers confirm the current format without relying on MotionCam's own decoder for pixel data. vkdt's `i-mcraw` module decodes blocks in its own GPU compute shader and uses the author's decoder only for container metadata. `libmcraw` is also useful, but it is based on the author's decoder rather than independent of it.

## 2. The container

An MCRAW file is a flat stream of typed items with an index at the end. The current container is version 3.

```
struct Header { uint8_t ident[7] = "MOTION "; uint8_t version = 3; }
struct Item   { uint32_t type; uint32_t size; }   // followed by `size` bytes
```

Item types in use include `BUFFER_INDEX` (0), `BUFFER_INDEX_DATA` (1), `BUFFER` (2), `METADATA` (3), four audio types (4 to 7), gyro (8, 9), OIS (10, 11) and accelerometer (12, 13).

**Worked example: a file holding two frames.**

```
"MOTION " 0x03                         8-byte header
Item{METADATA}  container JSON          camera description, recording settings
Item{BUFFER}    frame 0 pixel data      compressed payload
Item{METADATA}  frame 0 JSON            {"width":..., "height":..., "compressionType":7, ...}
Item{BUFFER}    frame 1 pixel data
Item{METADATA}  frame 1 JSON
... offset table: BufferOffset{int64 offset, int64 timestamp} x 2
Item{BUFFER_INDEX}  {int32 magic = 0x8A905612, int32 numOffsets = 2, int64 indexDataOffset}
```

To open a file, the decoder seeks to `EOF - sizeof(Item) - sizeof(BufferIndex)`, checks the magic number, and follows `indexDataOffset` to the offset table. Each frame is then one seek away. Loading a frame reads its `BUFFER` item, then the `METADATA` item behind it, and picks the codec from the JSON field `compressionType`.

**Recovery.** If the recording was cut off before the index was written, the decoder rebuilds it by walking the items from the start, checking that each declared size fits inside the file. A crashed take stays readable up to its last complete item. The archived writer is plain buffered stdio: `fdopen(fd, "w")` and `fwrite`, with no `fsync`, preallocation or direct I/O.

Current files carry a segment number (MotionCam's own sample file ends in `.0.mcraw`). In the 2022 archive, `nextSegment()` increments that number to name the second file of a split recording, so `X.0.container` is followed by `X.1.container` (section 6).

## 3. The codec, current generation

This is the whole of the current pixel codec, taken from `RawData.cpp`.

**Frame header.** 16 bytes of little-endian `uint32`: `encodedWidth`, `encodedHeight`, `bitsOffset`, `refsOffset`. The encoded width is a multiple of 64.

**Tiling.** The frame is walked in bands of 4 rows, and each band in tiles of 64 columns. One tile covers 4 × 64 pixels, which is 256 samples, and they are split by colour. With a 2×2 Bayer pattern, even and odd columns of rows 0 and 2 are two colours, and even and odd columns of rows 1 and 3 are the other two:

| block | samples taken from |
|---|---|
| p0 | rows 0 and 2, even columns (32 + 32) |
| p1 | rows 0 and 2, odd columns |
| p2 | rows 1 and 3, even columns |
| p3 | rows 1 and 3, odd columns |

Each block holds 64 samples of a single CFA colour. Grouping by colour matters because the four colours sit at different levels. Mixing them would widen every block's range.

**Reference and width.** Each block has a 16-bit reference and a bit width. Decoding is `sample = packed_value + reference`, where the packed values are unsigned integers of that width. For the encoder, this means the reference must be at or below the block's smallest sample, and the width must cover the largest sample minus the reference. Choosing the reference as the block minimum gives the narrowest width, and is almost certainly what the encoder does (inference: the encoder source is closed).

**Quantised widths.** Widths are rounded up to a small set so that each has a hand-written SIMD kernel:

| needed width | stored as | bytes for 64 samples |
|---|---|---|
| 0 (flat block) | 0 | 0 |
| 1 to 6 | same | 8, 16, 24, 32, 40, 48 |
| 7, 8 | 8 | 64 |
| 9, 10 | 10 | 80 |
| 11 to 16 | 16 | 128 |

A block needing 7 bits costs the same as one needing 8. Anything over 10 bits is stored raw at 16. Uncompressed RAW16 costs 128 bytes per 64 samples, so 128 is also the worst case.

**Side streams.** Widths and references aren't stored next to their blocks. They live in two arrays at `bitsOffset` and `refsOffset`, and those arrays are packed with the same reference-plus-width scheme. Each has a 2-byte header holding a 4-bit width and a 12-bit reference. Neighbouring blocks have similar references, so these streams compress well too.

**The codec has no prediction step, no entropy coder (Golomb-Rice, Huffman) and no escape codes.** Every block decodes with one of about ten fixed kernels that load 8 bytes, mask and shift, and store 8 values at a time. `RawData.cpp` is written with SSE intrinsics through SIMDe, which lets the same code run on ARM.

### Worked example: encoding one block

Take 64 green samples from a dark, flat patch of a 14-bit frame. The first eight are:

```
1024  1031  1021  1040  1033  1047  1028  1036   ...
```

Suppose the smallest sample in the block is 1021 and the largest is 1047.

1. **Reference** = 1021.
2. **Subtract:** `3  10  0  19  12  26  7  15 ...`
3. **Width:** the largest leftover is 26, which needs 5 bits (26 < 32).
4. **Pack** 64 values × 5 bits = 320 bits = **40 bytes**.

Stored as RAW16 those 64 samples take 128 bytes, so this block shrinks to 31%. Two other blocks show the range of outcomes:

- **A bright, noisy block**, samples between 9,000 and 9,900. The range is 900, which needs 10 bits, so 80 bytes (63%).
- **A block straddling a hard edge**, samples between 1,000 and 7,000. The range is 6,000, which needs 13 bits, rounded to 16, so 128 bytes: no saving at all.

That is how the codec adapts. Dark and flat areas get a handful of bits, noisy areas get more, and an edge costs full width, but only in the one 64-sample block it crosses.

## 4. How the codec got here

The archived 2022 app gives the history. Its compression enum reads:

```cpp
enum class CompressionType : int {
    UNCOMPRESSED, ZSTD, V8NZENC, P4NZENC, BITNZPACK, BITNZPACK_2, MOTIONCAM, INVALID
};
```

`MOTIONCAM` sits at index 6, the number today's decoder assigns to the legacy format. So the 2022 app wrote what is now legacy, and the current format was added later as type 7. The earlier entries show what was tried first: zstd, a general-purpose compressor, and three integer codecs. `BITNZPACK` matches the `bitnzpack` functions declared in TurboPFor's `include/ic.h`; `V8NZENC` and `P4NZENC` follow the same naming, though they did not turn up in the headers checked for this article. TurboPFor is a library of SIMD integer codecs built on frame-of-reference, delta and zigzag transforms. The path runs from a general compressor, through general integer codecs, to a bitpacker built around the Bayer pattern.

**The legacy format** (`RawData_Legacy.cpp`) works one row at a time in 32-pixel blocks. Each block splits into two 16-sample blocks for the even and odd columns, which are the two colours on that row. Each block carries an inline 2-byte header, and widths run 0 to 10 in single-bit steps, with 16 for anything wider. A trailing table of decode offsets, marked with `0xFF`, lists positions in the frame, probably so that it can be decoded in parallel (inference).

**What changed for the current format:**

| | legacy (type 6) | current (type 7) |
|---|---|---|
| block | 16 samples, one row | 64 samples, two rows of one colour |
| grouping | 2 colours per row | full 2×2 Bayer period per tile |
| header | inline, 2 bytes per block | widths and references in separate packed streams |
| widths | every value 0 to 10, then 16 | 0 to 6, 8, 10, 16 |
| decoder | scalar loops | SIMD kernel per width |

Header cost is the clearest gain. Legacy pays 2 bytes per 16 samples, 1 bit per sample before any data. The current format moves headers into streams that compress, and spreads them over four times as many samples.

## 5. Why it is fast

**Fixed width per block, not per sample.** A variable-length code such as Golomb-Rice gives each value its own number of bits, so the position of value *n* depends on every value before it. Writing that is a serial bit-by-bit append, and reading it is a serial walk. A fixed width per block means every value's position is known in advance: block offset plus *i* × width. Packing and unpacking become arithmetic on whole machine words.

**Blocks are independent.** Given a block's offset, width and reference, it decodes without reference to any other block. vkdt exploits this fully: it precomputes those three arrays on the CPU and decodes every block of a frame at once in a GPU compute shader, with groups of 32 GPU threads each extracting a fixed bit position. That cannot be done with a serial variable-length stream.

**The worst case is known.** A block can never exceed 128 bytes for 64 samples, the size of RAW16. The archived pipeline relies on a bound like this: `encode(data, ...)` compresses the frame inside the same buffer it arrived in and returns where the data ends, and there is no separate output buffer or uncompressed fallback copy. The decoder alone doesn't show how MotionCam guarantees the side streams also fit, so treat the exact bound as unverified.

**Few threads.** The archived app starts only `NUM_COMPRESSION_THREADS = 2` compression workers, or 3 above 30 fps. The codec is cheap enough that two cores keep pace at 4K.

**What it gives up.** Predictive coding plus an entropy coder squeezes harder. A published FPGA Bayer compressor using prediction and adaptive Golomb-Rice reaches up to 56% size reduction; to hit 40 Gbit/s its authors built a pipeline that codes 16 pixels in parallel. Guides to MotionCam Pro describe MCRAW as saving "up to 50%", a second-hand best-case figure rather than a measurement. If it is roughly right, prediction adds only a few points on noisy RAW data. The fixed-width design gives up some compression ratio for much less CPU time, which on a phone also means less heat.

## 6. The capture pipeline

In the 2022 archive the path from sensor to disk has five stages. Each hands off through a lock-free queue (moodycamel `ConcurrentQueue`).

**Stage 1: the ImageReader callback does almost nothing.** It wraps the `AImage` in a `shared_ptr` whose deleter is `AImage_delete` and pushes it onto a queue. The camera thread never blocks.

**Stage 2: a copy thread moves the frame into RAM it owns.** It takes a free buffer from the pool, copies the pixel plane in (`std::copy`), copies the metadata, and lets the `AImage` go back to the reader. Android's `ImageReader` lends out a fixed, small number of images, and an app that holds them while it works can never buffer more than that. Once MotionCam has copied a frame, only the size of its own pool limits how many frames can wait.

**Stage 3: the pool.** `RawBufferManager` holds pre-allocated buffers. They are grown or shrunk four at a time until memory use reaches `maxMemoryUsageBytes`, and the limit can be changed while the camera runs. The setting is `raw_video_memory_use_megabytes`, from 512 to 4096 MB in the settings UI. The archive disagrees with itself on the default: the settings screen assumes 1024 MB, but the code that reads the preference falls back to 512 MB when it was never saved.

**Stage 4: compression threads.** Two or three workers take frames from the pool, crop and compress each one in place (cropping is part of the `encode` call, and 2×2 binning is optional), and pass them on.

**Stage 5: one I/O thread per output file.** Each writer thread owns one container file and appends frames with buffered `fwrite`, then returns each buffer to the pool. The archive asks for `SCHED_FIFO` priority 99 on these threads but ignores the return value. Ordinary Android apps normally aren't allowed real-time scheduling, so this request probably fails silently (unverified).

**Split writes.** With "use secondary storage" enabled, the app creates a second file (`X.1.container` beside `X.0.container`) in a second user-chosen location, and a second I/O thread writes it. This doubles write capacity only if the two locations are separate physical devices, for example internal storage plus a USB SSD. Two threads writing the same flash chip mostly compete with each other.

### Worked example: how long the buffer lasts

The pool counts **buffers**, and every buffer is the size of an uncompressed camera frame, even after compression shrinks the data inside it. Compression lets frames reach disk faster. It does not let the pool hold more of them.

A 4096 × 3072 RAW16 frame is 25.2 MB. A 1 GB pool holds about 42 of them.

```
seconds until drops = frames in pool / (capture fps - fps the pipeline sustains)
```

| capture | pipeline sustains | deficit | 1 GB pool (42 frames) | 4 GB pool (170 frames) |
|---|---|---|---|---|
| 24 fps | 24 fps | 0 | never | never |
| 24 fps | 20 fps | 4 fps | 10 s | 42 s |
| 60 fps | 45 fps | 15 fps | 3 s | 11 s |

Two things follow. A buffer turns a small deficit into a long grace period, but it can't fix a large one. And a pool only fully refills when the pipeline runs faster than capture, which happens between takes, not during them.

## 7. Where MotionCam still loses frames

**When the pool is empty.** In the copy thread, the code for a missing buffer is:

```cpp
std::shared_ptr<RawImageBuffer> dst = RawBufferManager::get().dequeueUnusedBuffer();
// If there are no buffers available, we can't do anything useful here
if(!dst) {
    continue;
}
```

The pending `AImage` is released when the loop moves on, and the frame is gone. No drop counter is touched on that path.

**When storage can't keep up.** A Pixel 7 Pro owner on XDA reports that internal storage "can't handle more than 200Mb/S continuous write speeds". They add that 4K60 worked only "if you use the external storage option (split data)". On internal storage it lasted "30-60 seconds of video MAX", then "started dropping most of the frames when the memory buffer was full". Another user says "the STORAGE speed is the biggest bottleneck".

**When the phone throttles.** The same thread recommends a thermal-throttling mod, with which 4K60 had "only a few dropped frames compared to hundreds" without it. As late as November 2025, users were still asking how to record with MotionCam Pro without dropped frames.

These are user reports on particular phones, not measurements. They match the code exactly: the buffer absorbs deficits for a while, and storage and heat decide how big the deficit is.

## 8. RawCam next to MotionCam

| | MotionCam (2022 pipeline, current codec) | RawCam (main, September 2026) |
|---|---|---|
| Frame intake | callback enqueues; copy thread moves pixels into its own pool | ring of 8 `AImage*` held until processed (`capture.h:107`) |
| What limits buffering | pool size in MB | the `ImageReader`, created with `maxImages = 12` (`capture.cpp:540`) |
| Buffer depth at 4096×3072 | about 40 to 170 frames (1 to 4 GB) | about 11 frames (8 + finish queue of 2) |
| Codec | block reference + fixed-width bitpack | MED/LOCO-I prediction + Golomb-Rice |
| Adapts per | 64-sample block | band (one Rice parameter `k`) |
| Bitstream | fixed positions, SIMD | serial variable-length (`BitWriter`) |
| Compression threads | 2 (3 above 30 fps) | pool sized to the big and mid CPU cores |
| Where encoding writes | in place, inside the pool buffer | separate output, **plus** a full-frame fallback copy (~25 MB) on every frame (`capture.cpp:218-224`) |
| Files | one I/O thread per file; optional second device | one file |
| Container | typed items, JSON per frame, index at end | 512-byte header, fixed 64-byte frame records, rescan on recovery |
| Drops when | the pool is empty | the 8-slot ring is full |
| Size | "up to 50%" smaller (quoted in guides, unmeasured) | measured ~0.48 of RAW16 earlier; 14.71 MB/frame at 14-bit |

**RawCam's Rice stream is already almost fixed-width.** The round-5 encoder work found the Golomb-Rice pack stage using about 84% of encode CPU. It also found that 97.7% of residuals are coded with quotient q = 0, where each value takes exactly k + 1 bits. So nearly every residual in RawCam's stream is already fixed-width. RawCam pays for serial variable-length coding, the costliest part of its encoder, to handle the remaining 2.3%. MCRAW's design takes the same statistical fact to its conclusion: pick a width per block and deal with outliers by widening that one block.

**RawCam's measurements so far.** Early compressed-capture rounds lost 58 to 91% of frames at 4096×3072@24. One pre-round-5 stage measured 42.8 ms per frame cold and 47 ms hot, against a 41.6 ms budget. After round 5, a cold 60-second take landed 1443 of 1443 frames. But the same 14-bit configuration drops 3.05% when warm and 9.01% at thermal plateau, and truncating to 12 bits made drops at least 8.23 percentage points *worse*, even though files shrank 21%.

## 9. What RawCam should take from this

Ranked by expected value. Each comes with the experiment that should decide it before any code is committed.

**1. Copy frames out of the ImageReader into a byte-sized pool.** This removes the ceiling of about 11 buffered frames. It cannot fix a sustained deficit (section 6), but RawCam's warm deficit is small enough that a pool changes the outcome for ordinary takes. A 3.05% warm drop rate at 24 fps is about 0.7 fps short, so a 1 GB pool (42 frames) would last roughly a minute before the first drop, and about 19 seconds at the 9.01% plateau. Those are rough estimates from rates measured with the current pipeline. The extra copy costs less than it seems, because RawCam already memcpys every frame into `job.rawCopy`; a pool copy would replace that copy, not add to it.
*Experiment:* on a pre-heated phone, alternate takes with and without the pool (the ABBA order used for the bit-depth study) and compare drop rates at matched thermal positions.

**2. Prototype the block codec offline, on real frames.** Implement reference-plus-width packing over 64-sample same-colour blocks, and run it single-threaded against the current MED + Rice encoder on real 14-bit Xiaomi frames. Measure bytes per frame and milliseconds per frame. The CPU saving is likely large, since it drops the predictor and the serial bitstream entirely. The ratio penalty is unknown, and this experiment is the only way to learn it.
*Decide on the numbers:* whether a smaller CPU and heat load outweighs somewhat larger files on this hardware.

**3. If the block codec wins, encode in place and delete the fallback copy.** The fallback copy exists only because RawCam can't know in advance whether a Rice-coded frame fits its buffer. A fixed-width codec has a computable worst case, so a buffer with fixed headroom for the side streams makes the uncompressed fallback unnecessary.
*Experiment:* encode the least compressible frames available (bright noise, edges everywhere) and confirm the bound holds.

**4. Settle whether bytes or CPU drive RawCam's drops.** RawCam's own records disagree. A 2026-08-30 note concluded that the lever is bytes per pixel, not compressor speed. The 2026-09-09 study then found that fewer bytes (12-bit) increased drops. MotionCam's design bets on CPU cost.
*Experiment:* the codec prototype from item 2, run on-device in the ABBA design on a warm phone, answers this directly.

**5. Offer split writes to a second device.** This only helps users with external storage, and it adds complexity to recovery and export.
*Experiment:* none needed until items 1 to 3 are done. On internal storage alone, expect no gain.

**Don't copy:**
- **`SCHED_FIFO`**, which an app probably can't get
- **JSON metadata for every frame,** which is flexible but adds work on every frame
- **The assumption that compression enlarges the buffer.** In MotionCam's design it doesn't.

## 10. Common mistakes

- **Believing MotionCam never drops frames.** It drops when its pool empties, and says nothing when it happens.
- **Thinking compression lets a RAM buffer hold more frames.** Pool buffers are full-size. Compression speeds up draining, not storage.
- **Treating the 2022 archive as today's codec.** It writes type 6, the legacy format. Today's files are type 7.
- **Reading "up to 50%" as a measurement.** It comes from guides to the app, and "up to" describes the best case.
- **Mixing CFA colours in one block.** The four Bayer colours sit at different levels, and a block that mixes them has a wide range and packs badly. In the current format a tile is 4 rows × 64 columns, split by row parity and column parity.
- **Letting encoder and decoder width tables drift apart.** 7 must become 8, 9 must become 10, and 11 to 16 must become 16, with exactly those byte counts, or every later block decodes from the wrong position.
- **Assuming two files on one flash chip double throughput.** Split writes help only across two physical devices.
- **Measuring drop rates on a cold phone.** A cold phone often drops nothing in either arm, which shows nothing. RawCam's own data runs from 0.00% cold to 9.01% at plateau for one configuration. Pre-heat, alternate, and control for thermal drift.

## 11. Open questions

- **How the current encoder chooses references and widths,** and how it guarantees the side streams fit. The source is closed.
- **Current MotionCam Pro's pool defaults, thread counts and split behaviour.** Everything above is from 2022, and newer user reports only partly confirm it.
- **Whether `SCHED_FIFO` ever takes effect** for MotionCam's I/O threads on current Android.
- **What the legacy format's trailing offset table is for.** Parallel decode is the likely answer, but it is unconfirmed.
- **What compression ratio the block codec achieves on RawCam's own footage.** This matters most for RawCam, and only the item-2 experiment can answer it.
